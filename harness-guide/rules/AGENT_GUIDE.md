# Инструкция для агента

> Этот файл кладётся в проект и подключается из файла инструкций строкой
> `@<путь>/AGENT_GUIDE.md` либо копируется в него по разделам.
> Он написан для агента. Человеку объяснения даёт учебник, здесь только правила.
>
> Всё ниже - просьбы: ты читаешь их и решаешь, как применить. Правила, помеченные
> **[проверка]**, в исправном проекте дополнительно закрыты хуком, запретом в настройках
> или внешней системой. Узнать, есть ли проверка, можно так: хуки агента перечислены в
> `.claude/settings.json`, хуки git лежат в папке из `git config core.hooksPath`, защита ветки
> видна в настройках репозитория. Если проверки нет, скажи об этом человеку и предложи её поставить.

## 0. В начале каждой сессии

1. Выясни, чей это клон. Если с проектом работает один человек, владелец - он. Если людей
   несколько, проверь метку в настройках git (`git config --get project.owner`) и `whoami`.
   Метки нет - спроси один раз и предложи записать её: `git config project.owner <имя>`.
   Пока владелец не определён, веток не создавай и ничего не отправляй.
2. Покажи текущую ветку: `git rev-parse --abbrev-ref HEAD`.
3. Покажи `git worktree list` и ветки по дате последнего коммита, старые сверху:
   `git for-each-ref --sort=committerdate --format='%(committerdate:short) %(refname:short)' refs/heads`.
4. Если ты на `main` или в ветке без номера задачи, скажи об этом до любой правки и предложи
   создать ветку по номеру задачи. Номера нет - спроси, по какой задаче работа.
5. Прочитай файл статуса или последний комментарий задачи, если работа продолжается.

## 1. Задачи, ветки, коммиты

- Коммит и отправка - только по задаче из трекера. Нет задачи - сначала заведи её или
  попроси человека. Работа без номера остаётся в рабочей папке.
- Ветка: `<владелец>/<номер>-<описание>`. Одна задача - одна ветка - один запрос на слияние.
- Заголовок коммита: `тип(область): описание (#номер)`. Типы: feat, fix, docs, refactor, chore. **[проверка]**
- Правки по двум задачам в один коммит не кладутся.
- В `main` напрямую не пишешь: ни коммитом, ни `git push origin HEAD:main`. **[проверка]**
- Чужие ветки не трогаешь: не переключаешься на них, не коммитишь, не удаляешь.
- Свежую `main` берёшь в свою ветку так: пока ветка не отправлена - `git pull --rebase origin main`;
  после отправки - `git merge origin/main`, чтобы не переписывать отправленную историю.
  В локальную `main` ничего не вливаешь.
- `--no-verify` и `--force` не используешь. Если проверка мешает, скажи человеку, что именно
  она остановила.
- Запрос на слияние открывает и вливает человек. Ты даёшь ветку, описание и ссылку.
- В автоматическом коммите никогда не `git add -A`. Только поимённый список путей.
- Влитую ветку и свою рабочую папку после слияния удаляешь без вопроса: это уборка, а не
  удаление из раздела 7. Невлитую ветку не удаляешь: показываешь `git diff main...<ветка>`
  и ждёшь решения.

## 2. Параллельная работа

- Две сессии в одной рабочей папке не работают. Нужна вторая - создай worktree.
- Перед правкой проверь, не меняет ли кто-то эти файлы: `git status`, время изменения.
- В новую рабочую папку не попадают файлы, закрытые от git. Не найден нужный файл -
  не создавай пустой, скажи человеку.
- Сервис не запускается из рабочей папки. Только из выкаченной версии.

## 3. Файлы и структура

- Куда класть файл и как его назвать - по файлу правил хранения проекта. Не нашёл правила -
  спроси, не изобретай.
- У файла один адрес. Подходит под две папки - это два разных файла.
- В корень проекта рабочие файлы не кладёшь. Исключение - файл хода настройки
  `harness-setup-status.md`, пока идёт настройка по гайду; он коммитится вместе с остальным.
- Пустую папку заранее не создаёшь. Папка появляется с первым файлом.
- Устаревший файл не переименовываешь и не удаляешь: кладёшь рядом новый, а в старый
  первой строкой ставишь ссылку на него.
- Перед первым коммитом новой папки: `git check-ignore -v <путь>` и
  `git status --porcelain -uall | wc -l`. Число неожиданно большое - стоп.
- Разовый код: если он что-то пишет, перемещает или удаляет, либо длиннее тридцати строк,
  сохрани его файлом и запусти файл. Код прямо в команде допустим, только когда он разовый,
  ничего не меняет и результат целиком виден в ответе.

## 4. Секреты

- Не проси человека прислать ключ в чат. Дай готовую команду с пустым местом и скажи,
  в какой файл на машине вписать значение.
- Если ключ появился в разговоре, скажи сразу: он считается утёкшим, его надо перевыпустить.
- Не читаешь файлы с секретами без прямой необходимости. **[проверка]** Запрет в настройках
  закрывает только твоё прямое чтение. Скрипт, который ты запускаешь, тоже не должен их открывать
  и печатать.
- Значения секретов не печатаешь: ни в ответе, ни в журнале, ни в коммите, ни в отчёте
  помощника. Для проверки наличия печатай имя и длину. Контрольную сумму не
  печатай: короткое значение по ней подбирается перебором.
- Новый сервис берёт ключ из общего файла секретов. Свой файл с ключами рядом с кодом
  не заводишь.
- Имя новой переменной добавляешь в файл-образец с комментарием: зачем она и где её взять.
- Нашёл секрет в репозитории, в истории или в копии файла - остановись и скажи человеку
  до любых других действий.

## 5. Сервер

- Под root не работаешь. **[проверка]** Единственное исключение - первый вход на новый сервер,
  чтобы создать личные учётные записи. Если под root приходится делать что-то ещё, скажи об
  этом как о проблеме.
- Каждому сервису - свой служебный пользователь и свой юнит со строкой `User=`.
- Широких прав не выдаёшь: ни `NOPASSWD: ALL`, ни группу `docker`. Нужно право администратора -
  предложи точную команду и объясни, зачем.
- Код кладёшь в папку версий, настройки и секреты в `/etc/<проект>/`, данные в
  `/var/lib/<проект>/`. Из `/tmp` и домашних папок ничего не запускается.
- На сервере файлы кода не правишь. Исправление идёт через репозиторий и выкатку.
- Порт публикуешь на `127.0.0.1`, если человек прямо не сказал открыть его наружу.
- После изменения настроек проверяешь действующее состояние, а не свой файл:
  `sshd -T`, `ss -tulpn`, `systemctl show`.
- Настройки входа меняешь, только пока открыта вторая рабочая сессия.
- Ничего не удаляешь на сервере по своей инициативе. Составь опись: что это, кто создал,
  какой сервис пользуется, что будет при удалении, твоё предложение. Решает человек.

## 6. Выкатка

- На сервер уезжает только `main`.
- Новый сервис добавляется в общий скрипт установки. Своего установщика не приносишь.
- Скрипт установки проверяешь двумя запусками подряд.
- У сервиса есть проба. Она говорит числами: сколько прочитано из скольких. Сервис
  включается только после успешной пробы. Не хватает условий - сервис выключен, причина названа.
- Что нельзя сделать кодом, пишешь списком действий для человека.
- После копирования - перезапуск. После перезапуска - запрос к сервису. Сообщению команды
  об успехе не веришь, проверяешь состояние.
- Изменение базы, которое что-то удаляет, не применяешь без явного решения человека.
- Выкатку исполняет скрипт. Ты его пишешь и проверяешь, но не заменяешь собой.
- Нет предыдущей версии для отката - скажи до выкатки.

## 7. Что включает только человек

Ты строишь, проверяешь в режимах пробы и холостого прогона, говоришь, чего не хватает,
и останавливаешься. Перевести в рабочее состояние без явного указания человека нельзя:

- отправку и публикацию наружу;
- всё, что тратит деньги;
- удаление, перезапись истории, отзыв доступа;
- изменение прав, ключей, пользователей, настроек входа;
- снятие блокировок и исключения из правил;
- вход в чужие сервисы и аккаунты. Туда входит только человек.

Старое или общее разрешение не считается. Одно поручение - одно действие.

## 8. Модель в автоматизации

- Шаг, который должен быть одинаковым каждый раз, пишешь обычной программой.
- Модель ставишь там, где нужны суждение или язык. После неё - проверка программой.
- В сервисе модель вызывается через API, через одну общую функцию. Себя или другого агента
  из командной строки в рабочий путь сервиса не ставишь.
- У вызова есть ограничение по времени, у прогона - потолок, у ключа - предел расходов.
- Ответ модели запрашиваешь по схеме и проверяешь значения, а не только форму.
- Ответ внешнего сервиса проверяешь сразу при получении. Ошибка может прийти со статусом успеха.
- Массовую операцию сначала запускаешь на трёх примерах.
- Перед постройкой проверки измеряешь, как часто проблема случается, и называешь число.
- Новую проверку испытываешь на заведомо плохом примере.

## 9. Как отвечать

- В рабочих документах и во всём, что уходит наружу, факт несёт ссылку на источник или
  пометку `[?]`; цифры, даты, имена и цитаты не по памяти. Для черновиков и набросков это
  не требуется. Не знаешь, какой уровень строгости у проекта, - спроси.
- «Не проверено» и «не найдено» - разные ответы. Не смешивай.
- На вопрос «нормально же?» - сначала сильнейший довод против, потом за, потом вывод.
- Ответ не начинается с похвалы.
- Позиция меняется на новый факт или довод. Несогласие без довода её не меняет.
- «Не знаю, проверить можно там-то» - допустимый ответ. Проверка занимает меньше минуты -
  проверь.
- Сообщая о результате, говори, что проверено и чем, а что нет. Упавшее называй упавшим.
- Увидел «странно, тут должно быть другое» - сначала спроси, не задумано ли так.

## 10. Контекст

- Одна задача - одна сессия. Перед завершением запиши состояние в задачу или файл статуса.
- Не загружай заранее то, что может не понадобиться. Читай по мере нужды.
- Код длиннее нескольких строк не печатаешь в команде и не вставляешь в текст скилла: кладёшь
  файлом и вызываешь по пути. Тогда в контекст попадает короткая команда и вывод, правка меняет
  пару строк вместо перепечатки всего кода, а запуск можно повторить и проверить.
- Вывод команд ограничиваешь: итог и числа, а не весь файл или журнал. Большой файл и PDF
  читаешь по частям, которые нужны.
- Помощнику пиши задание так, чтобы он понял его без этого разговора: цель, что уже
  исключено, какие файлы читать, что вернуть.
- От помощника требуй ссылку на открытую страницу. Пересказ поисковика источником не считается.
- В память записывай только то, что изменит твоё поведение в будущих сессиях и переживёт
  текущую задачу. Отчёты о сделанном туда не идут.
- Заметил, что инструкция ведёт по несуществующему пути, - скажи человеку. Не чини молча.

## 11. Когда остановиться и спросить

- владелец клона не определён;
- ты на `main` и нужно коммитить;
- найден секрет там, где его быть не должно;
- проверка или хук остановили действие, и причина неясна;
- действие из раздела 7;
- число файлов в коммите или строк к удалению неожиданно большое;
- задача требует права шире, чем у тебя есть;
- правило из этого файла противоречит файлу инструкций проекта. Назови оба места.

## 12. Как писать хуки и проверки

- Хук ставишь на то, что нельзя нарушать никогда. Предпочтение остаётся строкой в инструкции:
  сорок хуков перестают читать так же, как сорок правил.
- Блокирует действие только код возврата 2. Любой другой ненулевой код действие пропускает,
  поэтому при собственной ошибке хук тоже выходит с кодом 2.
- Ошибки в хуке не глушишь: никаких `2>/dev/null` и `|| true` на проверяющей команде.
- Новый хук испытываешь на заведомо плохом примере и показываешь человеку, что он сработал.
  Тишина на чистых данных ничего не доказывает.
- Хук git кладёшь в `.githooks/`, делаешь исполняемым (`chmod +x`) и включаешь через
  `git config core.hooksPath .githooks`. Неисполняемый хук git пропускает молча.
- Хук, который срабатывает часто (на каждый ответ, на каждую команду), ограничиваешь по времени
  и держишь быстрым.
- Хук молчит, пока всё в порядке, и говорит одной понятной строкой, что остановил и что делать.
- Чужой хук читаешь целиком до установки: он выполняется с правами человека.
- В описании хука пишешь, чего он не ловит. Хук - страховка от промаха, а границу держат
  права пользователя и защита ветки на сайте репозитория.
- Отключить или ослабить проверку можно только по прямому слову человека. Если проверка мешает,
  называешь, что именно она остановила.
